# Синхронизация касс через Firebase: настройка

Этот документ для владельца магазина (или того, кто настраивает кассы). Он описывает,
как подготовить облако Firebase, подключить первую кассу и добавить остальные.
Техническое описание: `docs/specs/firebase-sync.md` (облако) и
`docs/specs/multi-register-sync.md` (движок), решения D-025 и D-026 в `DECISIONS.md`.

## Как это устроено (коротко)

- Каждая касса работает со своей локальной базой и **продолжает работать без интернета**.
- Когда связь есть, касса отправляет свои изменения в облако и забирает чужие
  (каждые 30 секунд и через 3 секунды после продажи).
- Облако — проект **Firebase** от Google: вход по e-mail и паролю (Firebase Authentication)
  и база Cloud Firestore, где по каждому магазину хранится только журнал изменений.
  Облако ничего не удаляет и не «склеивает»: всё сводят сами кассы.
- Доступ к магазину есть только у учётных записей — участников магазина: это проверяют
  правила безопасности Firestore (файл `firebase/firestore.rules`).
- У каждой кассы есть буква: `A`, `B`, `C`… Номера документов на кассах с синхронизацией
  имеют вид «Чек №A-15», поэтому номера разных касс никогда не совпадают.
- Остатки, долги, бонусы и балансы подарочных карт каждая касса пересчитывает из журналов
  движения, поэтому на всех кассах они одинаковые.

## 1. Создайте проект Firebase (сначала ТЕСТОВЫЙ)

> Тестовые и рабочие данные нельзя смешивать. Начните с **отдельного тестового проекта**,
> проверьте на нём всё, и только потом создавайте рабочий проект.
> Тестовый проект уже создан: `dreampos-test-uz26` (база Firestore в регионе `nam5`,
> правила из шага 2 загружены). Для него осталось выполнить шаги 3 и 5.

1. Откройте https://console.firebase.google.com под своей учётной записью Google и нажмите
   **Создать проект** (*Create a project*).
2. Название, например, `dreampos-test` (для рабочего потом: `dreampos-prod`). Firebase
   добавит к ID проекта случайный хвост, например `dreampos-test-uz26` — это и есть
   **ID проекта**.
3. Google Analytics для синхронизации не нужен — его можно отключить.
4. В проекте откройте **Build → Firestore Database → Create database**:
   - режим **Production mode** (всё закрыто, доступ откроют наши правила на шаге 2);
   - **регион**: для тестового — любой; для **рабочего — в Европе** (например,
     `eur3 (europe-west)` или `europe-central2`). Регион потом изменить нельзя.

Тариф **Spark** (бесплатный) подходит для начала, см. «Ограничения бесплатного тарифа».

## 2. Загрузите правила безопасности

Правила разрешают доступ только участникам магазина, запрещают удаление и изменение
журнала и проверяют каждое изменение (см. `firebase/firestore.rules`).

Способ 1 — Firebase CLI (рекомендуется: загружает и правила, и настройки индексов):

```powershell
npm install -g firebase-tools      # один раз (нужен Node.js)
firebase login                     # один раз, вход учётной записью Google
cd <папка программы DreamPOS>      # там, где лежит firebase.json
firebase deploy --only firestore --project <ID проекта>
```

Должно появиться «Deploy complete!». Команду можно повторять: данные она не трогает.

Способ 2 — вручную: **Firestore Database → Rules**, замените весь текст содержимым файла
`firebase/firestore.rules` и нажмите **Publish**. (Так не загружается исключение поля
`payload` из индексов — это лишь немного увеличивает место в базе.)

> Без правил (или со старыми) касса при создании магазина покажет «Ошибка сервера
> синхронизации (HTTP 403 PERMISSION_DENIED (create_store))».

## 3. Включите вход по e-mail и создайте учётную запись владельца

1. **Build → Authentication → Get started**.
2. Вкладка **Sign-in method** → **Email/Password** → включите первый переключатель
   **Email/Password** (второй, «Email link (passwordless sign-in)», не нужен) → **Save**.
3. Создайте учётную запись владельца — одним из двух способов:
   - **из программы** (проще): на шаге 6 в окне «Подключение к облаку» выберите
     **«Создать аккаунт владельца»** (в мастере первого запуска — ссылка
     «Нет аккаунта? Зарегистрироваться») и введите e-mail, пароль (не короче 8 символов)
     и его повтор. Касса создаст учётную запись в вашем проекте и сразу войдёт в неё.
     **Пока не выключайте регистрацию** (пункт 4): её выключают уже после создания
     владельца — об этом напомнит шаг 6 и сама программа;
   - **в консоли**: **Users → Add user** — e-mail и пароль владельца.
4. После того как владелец создан, закройте самостоятельную регистрацию:
   **Authentication → Settings → User actions** — снимите **Enable create (sign-up)**.
   Если владельца вы создаёте из программы, сделайте это **после шага 6** (там же напоминание).

   > По умолчанию (в том числе на бесплатном тарифе **Spark**) самостоятельная регистрация
   > в новом проекте **открыта**: любой, кто узнает Web API key, может завести учётную
   > запись. Чужие магазины он не увидит (доступ решают правила из шага 2), но сможет
   > создавать свои и тратить бесплатную квоту. Поэтому после регистрации владельца её
   > нужно выключить.
   > Когда регистрация выключена, кнопка «Создать аккаунт» в программе покажет «В проекте
   > Firebase отключена регистрация новых аккаунтов» — тогда добавляйте пользователей
   > через **Users → Add user** (или временно включите переключатель обратно).

Этим e-mail и паролем вы будете входить в облако с каждой кассы. Касса **не сохраняет
пароль**: она хранит только токен входа. Если токен перестанет действовать (пароль сменили,
учётную запись отключили), касса попросит войти снова.

## 4. (Необязательно) Ограничьте Web API key

Web API key — не секрет: он лишь указывает на проект, а доступ к данным решают учётная запись
и правила. Его можно дополнительно ограничить в Google Cloud Console → **APIs & Services →
Credentials** → ключ → **API restrictions**: оставьте *Identity Toolkit API*,
*Token Service API* и *Cloud Firestore API*.

## 5. Узнайте ID проекта и Web API key

Значок шестерёнки → **Project settings** → вкладка **General**:

- **Project ID** — например, `dreampos-test-uz26`;
- **Web API key** — строка вида `AIzaSy…` (39 символов).

Если вместо ключа написано «No Web API Key for this project», сначала выполните шаг 3
(включение Authentication создаёт ключ) или добавьте в проект веб-приложение (значок `</>`
на этой же странице) — ключ появится.

> Никогда не вводите в кассу и не пересылайте ключи сервисных аккаунтов
> (*Service accounts*, JSON-файлы с закрытым ключом). Они дают полный доступ ко всем данным
> в обход правил. Касса работает только с ID проекта и Web API key.

## 6. Подключите первую кассу (создание магазина в облаке)

Первая касса — та, на которой уже есть ваши данные (товары, клиенты, продажи).

1. Войдите владельцем или администратором → **Настройки** → **Синхронизация**.
2. Введите **ID проекта Firebase**, **Web API key** (шаг 5), e-mail и пароль (шаг 3) → «Войти».
   Если учётной записи владельца ещё нет, переключитесь на **«Создать аккаунт владельца»**:
   те же ID проекта и Web API key (если они уже вводились, подставятся сами), e-mail,
   пароль не короче 8 символов и его повтор → «Создать аккаунт». После этого окно
   продолжится так же, как после входа (у нового аккаунта магазинов нет, поэтому сразу
   выбрано «Создать магазин в облаке»).

   **Сразу после регистрации** закройте самостоятельную регистрацию (шаг 3, пункт 4):
   консоль Firebase → **Authentication → Settings → User actions** → снимите
   **Enable create (sign-up)**. Программа напомнит об этом под «Аккаунт создан». Вход
   уже созданного владельца и остальные кассы от этого не зависят.
3. Выберите **«Создать магазин в облаке»**:
   - название магазина;
   - **среда**: «Тестовый магазин» (`test`) или рабочий (`production`).
4. Касса получит букву `A` и отправит в облако **все** свои данные. При большой базе
   первая отправка может занять несколько минут; кассой можно пользоваться, отправка
   продолжится при следующей синхронизации.

Правила среды:
- Демо-база (с включённым демо-режимом) может подключиться **только** к тестовому магазину.
  Рабочий магазин её не примет.
- Тестовый магазин показывает постоянную метку «Тестовый магазин».
- Среду магазина нельзя изменить из программы. Если ошиблись — создайте новый магазин.

## 7. Добавьте остальные кассы (подключение к существующему)

Новая касса подключается к магазину **только с пустой базой** (без товаров, продаж,
клиентов). Две заполненные базы никогда не объединяются.

1. Установите программу на новую кассу.
2. В мастере первого запуска выберите **«Подключиться к существующему магазину»**
   (или позже: **Настройки** → **Синхронизация** → **«Подключить к существующему»**).
3. Введите те же ID проекта, Web API key, e-mail и пароль, выберите магазин из списка.
4. Касса получит следующую букву (`B`, `C`, …), скачает все данные и откроет экран входа.
   Пользователи и их ПИН-коды приходят из облака, вход работает и без интернета.

Если до подключения на кассе прошёл обычный мастер первого запуска (создан свой владелец)
и подключение делается через **Настройки**, сотрудники, созданные на этой кассе,
**отключаются** после загрузки данных магазина: их ПИН-коды могли совпасть с ПИН-кодами
сотрудников магазина, и один ПИН входил бы под разными людьми на разных кассах. Входите
ПИН-кодами сотрудников магазина. Это видно в списке конфликтов («Сотрудники этой кассы
отключены»); нужного сотрудника можно включить снова с новым ПИН-кодом.

Если в базе уже есть данные, программа покажет причину и ничего не изменит.
Исключение — касса, которую отключили от этого же магазина (см. раздел 8).

### Дополнительная учётная запись облака (необязательно)

**Важно:** любая учётная запись облака, у которой есть доступ к магазину, — это полный
доступ владельца ко всем данным магазина: она видит всех пользователей (вместе с
хешами ПИН-кодов) и может изменить цены, настройки и пользователей сразу на всех кассах.
Поле `role` у участника только справочное, облако его не проверяет. Что кассир может
делать на кассе, определяют пользователи и ПИН-коды в самой программе.

Поэтому проще всего входить на всех кассах **одной** учётной записью владельца и вводить
пароль самим (владелец или доверенный администратор), не давая его кассирам. Если всё же
нужна отдельная учётная запись (например, для администратора филиала):

1. **Authentication → Users → Add user** — e-mail и пароль. Скопируйте его **User UID**
   (столбец в списке пользователей).
2. **Firestore Database → Data** → коллекция `stores` → найдите документ магазина (поле
   `name` — название магазина) и скопируйте его ID (это и есть ID магазина). Запомните его
   поле `environment` (`test` или `production`).
3. В документе магазина откройте подколлекцию `members` → **Add document**:
   Document ID = **User UID** нового пользователя, поля `role` (string) = `admin` и
   `addedAt` (timestamp) = текущая дата.
4. В корне базы откройте (или создайте через **Start collection**) коллекцию `users` →
   документ с ID = **User UID** → подколлекция `stores` → документ с ID = **ID магазина**,
   поля `name` (string) = название магазина и `environment` (string) = `test` или
   `production` (как у магазина). По этому документу магазин появится в списке на кассе.

Документы, созданные в консоли, правилами не проверяются — вводите ID без пробелов. Убрать
доступ: удалите в консоли оба документа (`members/<UID>` и `users/<UID>/stores/<ID магазина>`)
или отключите пользователя в Authentication.

## 8. Отключение кассы

**Настройки** → **Синхронизация** → **«Отключить»** (с подтверждением):

- синхронизация останавливается, токен входа и позиция загрузки стираются;
- **все локальные данные остаются**, буква кассы тоже;
- изменения, сделанные после отключения, не теряются: они уйдут в облако, если снова
  подключить эту кассу **к тому же магазину** («Подключить к существующему»: для кассы с
  данными в списке будет только этот магазин);
- в облаке ничего не удаляется.

Если отключённая касса создаёт **новый** магазин, она получает в нём новую букву (обычно
`A`). Номера документов всё равно не повторяются: программа продолжает нумерацию после
самого большого номера с этой буквой, который уже есть в базе.

### Восстановление резервной копии на подключённой кассе

Резервная копия содержит и данные синхронизации, **кроме токена входа в облако** (файл
копии могут унести на флешку, а токен даёт полный доступ к данным магазина в облаке).
Поэтому после восстановления на экране «Синхронизация» появится «Войдите снова»: войдите
той же учётной записью. При первой синхронизации касса сама заметит, что облако знает её
более поздние документы: она скачает их обратно (ничего не теряется), получит **новую
букву** и запишет это в список конфликтов («Копия базы кассы»). Если в промежутке на ней
успели оформить документ (чек, возврат, смену, приход, заказ, инвентаризацию, гарантийную
заявку) с уже занятым номером, он получит номер вида `B~1A2B-16` (тоже виден в
конфликтах). То же произойдёт, если файл базы подключённой кассы скопировать на другой
компьютер.

## 9. Переход с тестового проекта на рабочий

1. Создайте **отдельный** проект Firebase (`dreampos-prod`) с базой Firestore **в Европе**
   и повторите шаги 2–5 (правила: `firebase deploy --only firestore --project <ID рабочего
   проекта>`).
2. На кассе, где лежат **настоящие** данные, создайте рабочий (`production`) магазин.
   База, которая была подключена к **тестовому** магазину, для этого не подойдёт: в ней
   могут быть тестовые чеки и товары других касс, и программа не даст создать из неё
   рабочий магазин. Обучайтесь на демо-базе или на отдельной установке.
3. Остальные кассы подключайте к нему с пустой базой.
4. Тестовый проект можно оставить для обучения.

## Ограничения бесплатного тарифа (Spark)

Бесплатно в день на проект: **50 000 чтений** и **20 000 записей** документов Firestore,
1 ГБ хранения. Счётчики обнуляются в полночь по тихоокеанскому времени (около 13:00 по
Ташкенту, 14:00 по Бишкеку). Примерный расход (измерено на программе):

- продажа из *k* строк — это около **2 + 3k изменений** (чек, строки, движения остатка,
  остаток товара, оплата): 1 строка — 5 изменений, 3 строки — 11;
- **записи**: изменения + 2 на каждую отправку. Продажа из 3 строк ≈ 13 записей →
  около **1 500 таких продаж в день**;
- **чтения**: при отправке ≈ число изменений + 6, и **каждая касса** потом читает каждое
  изменение один раз. Две кассы, продажа из 3 строк ≈ **40 чтений**;
- **каждая проверка облака** стоит число полученных изменений + 1 чтение (правила доступа
  проверяют членство в магазине, и Firestore считает эту проверку чтением);
- **простой**: каждая открытая касса проверяет облако раз в 30 секунд — 2 чтения даже при
  пустом ответе, то есть до **5 760 чтений в сутки** (около 2 880 за 12 часов работы).
  4 кассы, открытые круглосуточно, тратят на простой около 23 000 из 50 000 чтений;
- итого для 2 касс, открытых по 12 часов: около 5 800 чтений на простой + 40 на продажу —
  примерно **1 000 продаж по 3 строки в день**.
- **Первая загрузка** («Создать магазин в облаке») записывает **каждую** строку базы, а
  новая касса при подключении **читает** весь журнал. База больше ~20 000 строк не
  загрузится за один день: синхронизация остановится с ошибкой сервера
  `HTTP 429 RESOURCE_EXHAUSTED` и продолжится сама после обнуления квоты. Кассы при этом
  работают как обычно.

Если квоты не хватает, переведите проект на тариф **Blaze** (оплата по факту: бесплатная
квота остаётся бесплатной, сверх неё — центы за 100 000 операций) и поставьте бюджетное
оповещение в Google Cloud Billing. Расход видно в **Firestore Database → Usage**.

## Ограничения (известные)

- **Продажа одного товара сразу на двух кассах без связи** может увести остаток в минус.
  Продажа не отменяется; после синхронизации появится уведомление и запись в списке
  конфликтов на экране «Синхронизация». То же для подарочной карты, потраченной дважды,
  и для бонусов.
- **Совпадение штрихкода / номера карты клиента**, заведённых на двух кассах без связи:
  значение остаётся у более поздней записи, у второй оно очищается (видно в конфликтах), и
  это очищение отправляется на все кассы. Если кассы рассудили совпадение по-разному
  (одна из записей успела измениться до отправки), значение может очиститься у обеих —
  задайте его заново.
- **Одновременное изменение одной записи** на двух кассах: остаётся более позднее изменение.
  Продажа, возврат или приход на другой кассе не отменяют правку владельца (цена, лимит
  долга, блокировка сертификата): остатки и балансы обмениваются отдельно от карточки.
- **Аннулирование чека на одной кассе и возврат по нему на другой** (без связи): чек
  остаётся аннулированным, но возврат тоже учтён — в конфликтах появится запись
  «Возврат по аннулированному чеку». Проверьте кассу и остатки. Так же отмечается возврат
  одной позиции на двух кассах сразу («Возврат больше продажи»).
- **Черновик заказа поставщику, изменённый на двух кассах** без связи: остаётся версия,
  сохранённая позже, целиком (строки другой версии скрываются и возвращаются, если позже
  победит их версия — например, заказ отправлен с двух касс).
- **Один и тот же документ, проведённый на двух кассах без связи** (сторно одного прихода,
  завершение одной инвентаризации, отмена одной оплаты поставщику, гарантийная замена со
  списанием): после синхронизации он учтён **один раз** — остатки и баланс поставщика не
  меняются дважды. Проведённая инвентаризация и сторнированный приход не возвращаются в
  черновик / «проведён» из-за правки на другой кассе. Если документ уже проведён на другой
  кассе, но пришёл не целиком, касса откажет с сообщением «уже проведён на другой кассе» —
  синхронизируйте её и откройте документ снова.
- **Повреждённое изменение в облаке** (записанное несовместимой или самодельной
  программой: значение не того типа, нет обязательного поля, невозможная версия)
  пропускается: синхронизация продолжается, в конфликтах появляется «Изменение из облака
  пропущено». Касса такие изменения и не отправляет, а правила облака проверяют версию и типы полей.
- **Отменить оплату поставщику наличными** можно только на той кассе, в чьей открытой
  смене она внесена: деньги возвращаются в её ящик.
- **Одинаковый ПИН-код у двух сотрудников** (заведены или изменены на двух кассах без
  связи): вход с этим ПИН-кодом не выполняется ни на одной кассе, программа просит
  сменить ПИН одному из них. Войдите другим владельцем/администратором и смените ПИН.
  Поэтому заводите сотрудников и меняйте ПИН-коды на одной кассе при работающей связи.
- Заказы поставщику, принятые в старой версии программы (до документов прихода), при
  обновлении получают документ прихода «Начальный остаток (синхронизация)» на уже
  принятое количество (на сумму 0, без движения остатков). Его нельзя сторнировать.
- Изменение, у которого ещё не пришла «родительская» запись (например, товар новой
  категории), ждёт её и применяется автоматически, синхронизация не останавливается.
- Средняя себестоимость при приходах одного товара на двух кассах без связи может
  немного отличаться от точной.
- Журнал действий (аудит) и уведомления остаются на каждой кассе свои.
- Облако не удаляет старые изменения; база Firestore со временем растёт (каждая продажа
  отправляет и строки товаров, клиентов и т. п.). Очистка журнала — отдельный будущий этап.
  1 ГБ бесплатного места хватает примерно на 1–2 млн изменений; объём видно в
  **Firestore Database → Usage**.
- Правила облака запрещают программе удалять магазины, кассы и журнал изменений. Удалить
  данные может только владелец проекта в консоли Firebase (не делайте этого с рабочим
  магазином: кассы этого не ожидают).

## Проверка на живом тестовом проекте (для разработчика)

После шагов 2–5 в ТЕСТОВОМ проекте (правила загружены, вход по e-mail включён, учётная запись
создана) можно проверить синхронизацию двух касс без запуска приложения. В PowerShell
(пароль вводится только в вашем окне и нигде не сохраняется):

```powershell
$env:DREAMPOS_FB_PROJECT = "dreampos-test-uz26"
$env:DREAMPOS_FB_API_KEY = "<Web API key>"
$env:DREAMPOS_FB_EMAIL = "<почта учётной записи тестового проекта>"
$env:DREAMPOS_FB_PASSWORD = Read-Host "Пароль"
flutter test test/live/firebase_live_test.dart
```

Тест создаёт в облаке новый магазин «Живой тест <дата>» с типом `test`, подключает две кассы,
проводит по продаже на каждой и проверяет, что остатки, номера (`A-1`, `B-1`) и все данные
совпали, а повторная отправка ничего не дублирует. Без этих переменных тест пропускается.
Каждый запуск оставляет в тестовом проекте свой магазин (несколько сотен записей из бесплатной
квоты).

## Если что-то не работает

| Сообщение / признак | Что сделать |
|---|---|
| «Нет связи» (offline) | Проверьте интернет. Касса продолжает работать и повторит попытку сама. |
| Неверный ID проекта | Скопируйте **Project ID** из шага 5 (строчные буквы, цифры, дефис), а не название проекта и не адрес сайта. |
| Неверный Web API key | Скопируйте **Web API key** из шага 5 заново (именно от **этого** проекта). Если ключ ограничен (шаг 4), проверьте список разрешённых API. |
| Web API key относится к другому проекту Firebase | ID проекта и Web API key взяты из разных проектов (например, ключ тестового проекта и ID рабочего). Скопируйте оба из шага 5 одного и того же проекта. Если это случилось при «Создать аккаунт», касса сразу удаляет учётную запись, случайно созданную в проекте ключа; если связи не было, проверьте Authentication → Users того проекта. |
| В проекте Firebase не включён вход по email и паролю | Шаг 3: Authentication → Sign-in method → Email/Password → Enable. Это же сообщение показывает «Создать аккаунт», если провайдер Email/Password выключен (Firebase отвечает OPERATION_NOT_ALLOWED). |
| Неверный email или пароль / нужно войти снова | Проверьте пользователя в Authentication → Users; при необходимости задайте там новый пароль и войдите заново в разделе «Синхронизация». |
| Аккаунт отключён в проекте Firebase | Authentication → Users → пользователь → **Enable account**. |
| Аккаунт с этим email уже есть | При «Создать аккаунт владельца» указан e-mail, который уже зарегистрирован в проекте: переключитесь на «Войти» (пароль можно сменить в Authentication → Users). |
| В проекте Firebase отключена регистрация новых аккаунтов | Снят **Enable create (sign-up)** (шаг 3, Firebase отвечает ADMIN_ONLY_OPERATION): создайте пользователя в Authentication → Users → Add user и войдите им, или временно включите переключатель. |
| Облако не приняло пароль: он слишком простой / этот email | Пароль короче 6 символов или адрес с ошибкой: исправьте и повторите. |
| Пароль не подходит под требования к паролям проекта | В проекте задана политика паролей (Authentication → Settings → Password policy: заглавные буквы, символы, длина). Придумайте пароль по этим требованиям или ослабьте политику. |
| Слишком много попыток регистрации | Firebase временно ограничил регистрацию с этого устройства/адреса. Подождите несколько минут. |
| Слишком много попыток входа | Firebase временно заблокировал вход после неудачных попыток. Подождите несколько минут или задайте новый пароль в Authentication → Users. |
| Нет доступа к магазину | Учётная запись не участник магазина: см. «Дополнительная учётная запись облака». |
| Ошибка сервера (… PERMISSION_DENIED (create_store)) | Правила не загружены или устарели: шаг 2. |
| Ошибка сервера (… NO_DATABASE …) | В проекте не создана база Firestore: шаг 1, пункт 4. |
| Ошибка сервера (… SERVICE_DISABLED …) | В проекте выключен Cloud Firestore API: создайте базу (шаг 1) или включите API в Google Cloud Console → APIs & Services. |
| Ошибка сервера (HTTP 429 RESOURCE_EXHAUSTED …) | Исчерпана дневная бесплатная квота: синхронизация продолжится после обнуления, или переведите проект на Blaze (см. «Ограничения бесплатного тарифа»). |
| Ошибка сервера (HTTP 5xx) | Временная проблема Google; касса повторит попытку сама. |
| Ошибка сервера (device_not_registered) | Касса не зарегистрирована в магазине (документ кассы удалён в консоли): отключите синхронизацию и подключитесь к магазину снова. |
| ПИН-код есть у нескольких сотрудников | Войдите другим владельцем/администратором и смените ПИН одному из них (Персонал). |
