# DreamPOS — статус проекта

_Обновлено: 2026-11-26_

**Продукт:** DreamPOS — offline‑first POS/ERP для розничных магазинов (Центральная Азия; интерфейс: русский, узбекский, кыргызский, английский).
**Стек:** Flutter 3.38 · Riverpod 3 · go_router · drift (SQLite). Решения — `DECISIONS.md`, структура и правила — `docs/ARCHITECTURE.md`, качество — `QUALITY_CHECKLIST.md`.
**Репозиторий:** https://github.com/farruhsho/DreamPos (ветка `main`).

## Как продолжить работу (новый сеанс)
1. Прочитать этот файл, `DECISIONS.md`, `docs/ARCHITECTURE.md`, `QUALITY_CHECKLIST.md`.
2. `flutter pub get` → `flutter analyze` → `flutter test` (ожидается: 0 замечаний, все тесты зелёные).
3. Визуальная проверка: `SCREENSHOTS=1 flutter test test/ux` → `build/screens/*.png` (файлы `.errors.txt` = ошибки вёрстки).
4. Схема БД изменилась → `dart run build_runner build -d --force-jit` (AOT‑режим падает из‑за build hooks sqlite3) и увеличить `schemaVersion` с миграцией в `onUpgrade`.
5. Запуск: `flutter run -d windows`. Первый запуск — мастер настройки (можно включить демо‑данные).

## Сделано
### Этап 1 — Фундамент ✅
- Схема БД: 34 таблицы, UUID, мягкое удаление, outbox для будущей синхронизации, schema v7 (документы прихода, взаиморасчёты с поставщиками, продажи сертификатов, синхронизация касс).
- Доменные сервисы с транзакциями: продажа, частичный возврат, аннулирование, смена X/Z, склад (журнал + средневзвешенная себестоимость), долги с лимитом, бонусы, сертификаты, вход по PIN, подтверждение менеджером.
- Движок цен: акции (товар/категория/N+M/чек/промокод), скидка клиента, лучшая без суммирования, ручные скидки с лимитом, распределение скидки по позициям, НДС, округление наличных.
- Поиск без учёта регистра для кириллицы на уровне SQLite.
- Резервное копирование: ручное, ежедневное автоматическое; безопасное восстановление при старте (проверка файла, старая база сохраняется).
- UI‑кит, тема (светлая/тёмная), встроенные шрифты, адаптивная оболочка, горячие клавиши, мастер настройки, вход по PIN.

### Этап 2 — Модули ✅
Касса · Чеки и возвраты · Гарантия · Товары (импорт CSV, ценники, EAN‑13) · Склад (приход, списание, инвентаризация, журнал) · Закупки (поставщики, заказы, частичная приёмка, автозаказ, контроль цен) · Клиенты/CRM (сегменты, долги, бонусы) · Маркетинг (акции, симулятор, сертификаты, рассылки) · Смена (X/Z‑отчёт, пересчёт купюр, внесения/выплаты) · Сотрудники (роли, PIN, рабочее время, мотивация, журнал действий) · Обзор · Отчёты (продажи, товары, ABC, сотрудники, оплаты, склад, прогноз спроса, AI‑инсайты, экспорт CSV/PDF) · Уведомления · Настройки.

Настройки подключены к кассе и товарам: округление наличных (вниз, только наличные), купюры быстрой сдачи, привязка устройства к кассе, срок долга, НДС по умолчанию, статус «Частично получен» для заказов.

### Этап 3 — Документы прихода и взаиморасчёты ✅
- `Приход №N` — документ (ручной и по заказу), № накладной поставщика, список с фильтрами, карточка, печать PDF, сторно с причиной (откат остатка, себестоимости, розничной цены, заказа поставщику).
- Журнал взаиморасчётов с поставщиком (`supplier_ledger`, D-021): приходы, сторно, оплаты, отмена оплат (наличные — только в открытой смене), корректировки (владелец/админ), акт сверки PDF/CSV за период.
- Спецификация: `docs/specs/receipts-and-supplier-ledger.md`. Независимый аудит: 9 подтверждённых дефектов исправлены (атомарная миграция v3, сальдо акта сверки, права на отмену наличной оплаты и др.).

### Этап 4 — Продажа сертификатов как документ ✅
- `Продажа №N` сертификата (D-023): аванс, не выручка — выручка признаётся при оплате сертификатом. Оплата наличными/картой/переводом/смешанная, сдача, бланк и чек (PDF/текст).
- Раздел «Сертификаты» в X/Z‑отчёте и ожидаемой наличности; блок «Продажа сертификатов (аванс, не выручка)» в отчёте по оплатам.
- Аннулирование неиспользованного сертификата с возвратом по исходным способам в текущей смене; кнопка «Продать сертификат» на кассе; список продаж сертификатов.
- Спецификация: `docs/specs/gift-card-sales.md`.

### Этап 5 — Локализация ✅
- Языки интерфейса (D-024): русский (по умолчанию), узбекский (латиница), кыргызский, английский. Таджикский убран по решению владельца.
- Все тексты в ARB (`lib/l10n/src/<модуль>/<язык>.arb`, 3036 ключей), сборка `dart run tool/l10n_merge.dart`; проверка забытых строк `dart run tool/l10n_check.dart` входит в тесты.
- Выбор языка: на экране входа, в мастере настройки и в Настройках → Оформление. Язык чека — отдельная настройка магазина (Настройки → Чек).
- Шрифты Roboto дополнены знаком «ʻ» (oʻ, gʻ) — `tool/patch_fonts_02bb.py`.
- Инструкция для разработчиков: `docs/L10N.md`; спецификация: `docs/specs/localization.md`.

### Этап 6 — Синхронизация нескольких касс ✅ (без живого сервера)
- Движок D-025, облако — Firebase (D-026, Firebase Authentication + Cloud Firestore через REST): изменения фиксируют триггеры SQLite, касса отправляет текущие строки и забирает общий журнал изменений по курсору; конфликты правок — «последняя запись побеждает» (гибридные часы), правки людей и учётные поля строки версионируются отдельно.
- Журналы — источник истины: остатки, долги, бонусы, балансы пересчитываются после приёма изменений; миграция выравнивает старые базы.
- Коды касс в номерах документов (`A-15`), смена принадлежит своей кассе, документ, проведённый на двух кассах, учитывается один раз.
- Офлайн‑конфликты (перепродажа, двойное списание сертификата, возврат аннулированного чека, совпадение штрихкодов/PIN) не блокируются, а попадают в журнал конфликтов на языке интерфейса и в уведомления.
- Тест и бой разделены: демо‑база — только в тестовый магазин; две непустые базы не объединяются; отключение не удаляет данные.
- Настройки → «Синхронизация», индикатор в верхней строке, подключение к магазину из мастера настройки. Облако: правила `firebase/firestore.rules` (загружены в тестовый проект `dreampos-test-uz26`), инструкция владельцу — `docs/SYNC_SETUP.md`, спецификации — `docs/specs/multi-register-sync.md` и `docs/specs/firebase-sync.md`.
- Четыре независимых круга ревью: 57 подтверждённых дефектов исправлены, каждый с тестом. Проверено на имитации сервера (2–3 кассы, случайные сценарии) и на эмуляторе Firestore REST в тестах; **на живом Firebase не запускалось** (нужна учётная запись в тестовом проекте, `test/live/firebase_live_test.dart`).

Каждый модуль: сборка → независимый аудит → визуальная проверка по скриншотам (3 размера) → повторная проверка свежим взглядом. Исправлено 194 визуальных дефекта.

## Не проверено
- Реальное оборудование: чековый принтер, сканер штрихкодов, денежный ящик.
- Android‑устройства (APK собирается, на устройстве не запускался). Windows release собирается и запускается; инсталлятора пока нет.
- Идентификаторы утверждены владельцем (D-020): Windows «Dream Dev / DreamPOS» (данные в `%APPDATA%\Dream Dev\DreamPOS`), Android `uz.dreamdev.dreampos`.

## Известные ограничения этапа 3
- Удалённого поставщика нельзя восстановить, поэтому его приходы нельзя сторнировать.
- Право отмены наличной оплаты (`cashInOut`) проверяется в интерфейсе, не в сервисе.

- Бесплатный выпуск сертификата (подарок/компенсация) отключён — только продажа; настройки `gift_quick_nominals`, `gift_receipt_note` пока без экрана настроек.

## Известные ограничения этапа 5
- Переводы uz/ky/en сделаны и проверены ИИ, не носителями языка — перед продажей стоит дать вычитать.
- На телефоне в узбекском и кыргызском метка смены в верхней строке обрезается многоточием.
- Тексты, уже записанные в БД (причины движений, журнал), и демо‑данные остаются на русском.

## Известные ограничения этапа 6
- Правила Firestore проверены компиляцией (`firebase deploy --dry-run`) и эмулятором в тестах; эмулятор Firestore не запускался (нужна Java 11+). Живой прогон — после включения входа по e-mail и создания учётной записи в тестовом проекте.
- Возврат по чеку, аннулированному на другой кассе: конфликт показывается, но товар и деньги остаются учтены дважды — исправляет владелец.
- Статистика клиента (сумма покупок, визиты), себестоимость и статус приёмки заказа — «последняя запись побеждает», одновременные изменения на двух кассах могут потерять одно увеличение.
- Журнал аудита не синхронизируется (у каждой кассы свой).
- При подключении базы к существующему магазину её прежние сотрудники отключаются (PIN нельзя сравнить — хэши с солью); владелец включает нужных заново с новым PIN.
- Кнопка отмены наличной оплаты поставщику из смены другой кассы видна, но сервис отказывает с сообщением.
- Количество, введённое в инвентаризацию на кассе без связи уже после её проведения на другой кассе, сохраняется в строке инвентаризации, но остаток не меняет (поправка остатка — по количеству на момент проведения).
- Совпадение штрихкода / карты клиента, которое кассы рассудили по-разному (запись успела измениться до отправки), очищает значение у обеих записей; конфликт показывается, значение задают заново.
- После восстановления резервной копии на подключённой кассе нужно снова войти в облако: токен входа в копию не попадает.
