# DreamPOS — Architecture Decision Log

Каждое решение: контекст → решение → последствия. Не меняйте принятые решения
без новой записи, которая явно отменяет старую.

## D-001 Платформа: Flutter, одна кодовая база
Касса на Windows (основной сценарий: ПК + сканер + чековый принтер), Android‑планшеты/телефоны
для мобильных продавцов и владельца. Flutter 3.38, Dart 3.10. Web пока не поддерживается
(drift на web требует wasm‑сборки sqlite — добавим при необходимости).

## D-002 Offline‑first: локальная SQLite (drift) — источник истины
Касса обязана продавать без интернета. Все операции пишутся в локальную БД
транзакционно. Облако — следующий этап (см. D-003).

## D-003 Готовность к синхронизации между кассами
Все синхронизируемые таблицы: UUID `id`, `createdAt`, `updatedAt`, мягкое удаление `deletedAt`.
Таблица `sync_outbox` фиксирует изменённые сущности (`db.markDirty`). Номера документов
(`counters`) локальные; при подключении сервера номер чека станет `<код кассы>-<номер>`.
Целевой бэкенд для синхронизации: Supabase (Postgres) — уже используется в других
проектах владельца. Не реализовано: сам транспорт синхронизации.

## D-004 Деньги — целые минорные единицы
`int` в минимальных единицах валюты. `CurrencyConfig.decimals` (UZS=0, TJS=2 …).
Никаких `double` для денег. Валюту нельзя менять после первой продажи.

## D-005 Остатки — журнал движений + кэш
`stock_movements` — неизменяемый журнал (sale/return/receipt/writeoff/adjustment/inventory).
`products.stockQty` обновляется в той же транзакции. Все изменения только через `StockService`.
Себестоимость — средневзвешенная, пересчитывается при приходе.

## D-006 Состояние и навигация
Riverpod 3 (провайдеры в `lib/core/providers.dart`), go_router (`lib/app/router.dart`),
адаптивная оболочка: NavigationRail ≥1000px, Drawer — уже.

## D-007 Доменные сервисы вне UI
`lib/domain/services/*` — вся бизнес‑логика продаж, возвратов, смен, долгов, склада.
UI никогда не пишет напрямую в таблицы sales/sale_items/stock_movements/customer_ledger.
Ошибки бизнес‑правил — `BusinessException` с текстом для пользователя.

## D-008 Политика скидок
Автоскидки по позиции не суммируются: берётся лучшая (акция на товар/категорию, N+M,
персональная скидка клиента). Ручная скидка кассира добавляется сверху и ограничена
`users.maxDiscountPercent`. Скидка на чек (акция/промокод/ручная) распределяется по
позициям пропорционально — это гарантирует точные частичные возвраты.
Цены включают НДС; НДС выделяется по позиции.

## D-009 Возвраты
Частичные возвраты по позициям; сумма возврата пропорциональна оплаченной сумме позиции,
последняя единица забирает остаток округления. Срок возврата — настройка `return_days`.
Начисленные бонусы списываются пропорционально. Аннулирование (void) — только чек без
возвратов и только в той же смене.

## D-010 Смены и касса
Продажа требует открытой смены (`require_shift`). Ожидаемая наличность =
размен + нал. продажи − нал. возвраты + внесения − выплаты/расходы/инкассации +
погашение долгов наличными − оплаты поставщикам наличными +
нал. продажи сертификатов − нал. возвраты по аннулированным продажам сертификатов (D-023).
Продажа сертификата считается в смене, где она проведена (даже если позже аннулирована),
аннулирование — в смене аннулирования. Выручка смены (`salesTotal`) сертификаты не включает.

## D-011 Безопасность
Вход по PIN (уникален среди активных сотрудников). Хэш: итерационный SHA‑256 с солью.
Блокировка после серии неверных попыток. RBAC: `lib/core/permissions.dart`.
Журнал аудита `audit_log` для чувствительных действий (скидки, возвраты, аннулирования,
корректировки остатков, касса).

## D-012 Язык интерфейса (заменено D-024)
Сейчас русский, строки в коде. Узбекский/таджикский/английский — отдельный этап
(вынос строк в ARB через gen-l10n). Не смешивать языки на одном экране.

## D-013 Демо‑данные отделены от боевых
Демо‑данные создаются только по явному флажку в мастере установки, ставят
`demo_mode=1`, на экране входа показывается метка «Демо‑режим».

## D-014 Реальные платёжные системы и фискализация не подключаются без согласия владельца
Оплата картой/переводом фиксируется вручную (сумма + ссылка). Интеграции с эквайрингом,
OFD/фискальными модулями (Uzbekistan OFD, и т.п.) — только после решения владельца.

## D-015 Округление наличных
Настройка `cash_rounding` (шаг в минорных единицах). Применяется только когда весь чек
оплачен наличными (`CheckoutRequest.applyCashRounding`), итог округляется ВНИЗ (в пользу
покупателя), разница распределяется по позициям как скидка на чек — возвраты остаются точными.
Округление не считается ручной скидкой кассира и не влияет на лимит скидки.

## D-016 Шрифты встроены в приложение
Roboto и RobotoMono (Apache 2.0) в `assets/fonts`, объявлены в pubspec и заданы в теме.
Одинаковая кириллическая типографика на Windows/Android, печать PDF офлайн.
`fontFamily: 'monospace'` не используется (на Windows это не моноширинный шрифт) — только
`AppFonts.mono`. Символ тенге (₸) отсутствует в Roboto → для KZT используется «тг».

## D-017 Регистронезависимый поиск по кириллице на уровне SQLite
На каждом соединении регистрируются Unicode‑версии `like`, `lower`, `upper`
(`lib/core/db/sql_functions.dart`). Все `LIKE` в приложении работают для кириллицы и узбекской
латиницы без изменений в модулях. При росте каталога >50k — FTS5 (отдельный этап).

## D-018 Подтверждение менеджером не является входом
`AuthService.verifyApprover` проверяет PIN без смены сессии, без `auth.login` и с отдельным
счётчиком неудачных попыток (`auth.approve_fail`). UI пишет `discount.approve`, сервис при
проведении чека — `discount.override`.

## D-019 Визуальный контроль качества
`test/ux/harness.dart` рендерит экраны с демо‑магазином в реальных шрифтах (desktop 1440,
tablet 1024, phone 390) в PNG; ошибки рендера сохраняются в `.errors.txt`. Каждый модуль имеет
`test/features/<m>/ux_screens_test.dart`. Запуск: `SCREENSHOTS=1 flutter test test/ux`.

## D-020 Официальные идентификаторы приложения (утверждено владельцем 2026-11-24)
Название продукта — DreamPOS, компания — Dream Dev. Windows: CompanyName «Dream Dev»,
ProductName «DreamPOS», данные в `%APPDATA%\Dream Dev\DreamPOS`. Android: `applicationId`
и namespace `uz.dreamdev.dreampos`. Идентификатор Android после публикации в магазине
не меняется — не трогать без новой записи в журнале решений.

## D-021 Документ «Приход» и журнал взаиморасчётов с поставщиками
Каждый приход (ручной и по заказу поставщику) — нумерованный документ `goods_receipts`
(`Приход №N`, счётчик `receipt`) со строками `goods_receipt_items`; проводится и сторнируется
только `ReceiptService` (одна транзакция). Движения склада прихода: `refType 'receipt'`,
`refId` = id документа; сторно — тип `receipt_reversal`. Любое изменение `suppliers.balance` —
только через `SupplierLedgerService` с записью в `supplier_ledger` (бегущий остаток
`balanceAfter`; инвариант — `balance` == Σ `amount` журнала, D-025: с несколькими кассами
`balanceAfter` — взгляд кассы, записавшей строку, и «`balance` == последний `balanceAfter`»
больше не гарантируется). Оплаты поставщику не удаляются, а отменяются
(`cancelledAt` + запись `payment_cancel`); отменённые оплаты не учитываются в кассе смены.

## D-022 Миграция v3 без переноса истории приходов
При обновлении схемы до v3 старые приходы не превращаются в документы (боевых данных ещё нет);
для поставщиков с ненулевым балансом создаётся запись журнала `opening` «Начальный остаток».

## D-023 Продажа сертификата — аванс, а не выручка; отдельный документ
Продажа подарочного сертификата — полученный аванс (обязательство), не выручка. Выручка
возникает при погашении сертификата в обычном чеке (оплата `gift_card`). Поэтому продажа
сертификата — нумерованный документ `gift_card_sales` («Продажа сертификата №N», счётчик
`gift_sale`) с оплатами `gift_card_sale_payments` (только наличные/карта/перевод), а не строка
`sales`: выручка, прибыль, ABC, мотивация и дашборд не меняются и ничего не считается дважды.
Пишет только `GiftCardService` (одна транзакция, markDirty, аудит `gift_card.sell` /
`gift_card.void_sale`). Всегда нужна открытая смена. Наличные не оформляются внесением
(`cash_movements`), а учитываются отчётом смены (раздел «Сертификаты», ожидаемая наличность)
и отчётом по оплатам отдельной строкой «Продажа сертификатов (аванс)». Аннулирование — только
неиспользованного сертификата (баланс = номинал, нет оплат им), с причиной, в открытой смене:
возврат теми же способами оплаты в смене аннулирования, сертификат блокируется с балансом 0 и
не удаляется. Сертификаты, выпущенные до схемы v4, остаются без документа (`soldSaleId = null`).

## D-024 Локализация интерфейса: ru / uz / ky / en (заменяет план D-012)
Решение владельца 2026-11-24: языки интерфейса — русский (шаблон, по умолчанию), узбекский
(латиница), кыргызский, английский; **таджикский не поддерживается**. Строки — в ARB через
gen-l10n, фрагменты по модулям `lib/l10n/src/<module>/<lang>.arb`, сборка
`dart run tool/l10n_merge.dart`. Язык интерфейса — настройка устройства (`ui_locale`), язык
чека — настройка магазина (`receipt_locale`, по умолчанию ru). Тексты, уже записанные в БД
(причины движений, аудит, журнал поставщика), не переводятся. Спецификация —
`docs/specs/localization.md`, инструкция для модулей — `docs/L10N.md`.

## D-025 Синхронизация касс через Supabase: журнал изменений, LWW, производные остатки
Изменения фиксируют триггеры SQLite (а не ручные `markDirty`) в `sync_outbox`; на сервер уходит
текущая строка целиком, сервер хранит единый журнал `changes` с порядковым номером, клиенты
забирают его по курсору. Конфликт правок одной строки — «последняя запись побеждает» по
гибридным логическим часам (версия + id устройства). Журналы (движения склада, долги/бонусы,
взаиморасчёты, оплаты) — источник истины; кэши (`stockQty`, балансы) не синхронизируются, а
пересчитываются из журналов после применения изменений; миграция v5 выравнивает журналы
записью «Начальный остаток (синхронизация)», инвариант D-021 ослаблен до «кэш = Σ сумм».
Номера документов получают код кассы (`A-15`), уникальность — по паре (код, номер). Офлайн‑
конфликты бизнеса (перепродажа остатка, двойное списание сертификата) не блокируются, а
показываются уведомлением и в журнале конфликтов. Демо‑база подключается только к магазину
`environment='test'`. Две непустые базы не объединяются. Сервер ничего не удаляет.
Спецификация — `docs/specs/multi-register-sync.md`.
После ревью (схема v6): строка делится на «правку человека» и «учёт» (остатки, балансы,
статистика — `statColumns`), у каждой части своя версия LWW, поэтому продажа на отставшей
кассе не откатывает цену/лимит/блокировку; аннулирование «липкое»; номера документов
продолжаются после максимального номера своей буквы; восстановленная или скопированная база
получает новую букву; изменение без пришедшего родителя откладывается, а не останавливает
загрузку; оплаты сертификатом хранят id карты. Подробности — раздел «Implementation notes»
спецификации.
Второе ревью: синхронизация сначала забирает, потом отправляет — новую букву получает только
копия/восстановленная база, а не работающая касса; долг «сменить букву» хранится и
выполняется при следующей синхронизации, если регистрация сорвалась; открытая смена базы,
сменившей букву (восстановление, новый магазин), остаётся её текущей сменой, а смены других
касс текущими не становятся. Аннулирование продажи, оплаченной сертификатом, не
разблокирует карту и не возвращает деньги на карту, чья продажа аннулирована. Черновик заказа
поставщику не возвращается в «черновик» после приёмки на другой кассе, а строки с приёмкой не
удаляются. Двойное аннулирование одной продажи сертификата и списание с аннулированного
сертификата показываются как конфликты. Журнал изменений базы, которая ни разу не
подключалась, очищается при открытии; добавлены индексы журнала и оплат сертификатами.
Третье ревью (схема v7): вход по ПИН-коду (время входа, счётчик ошибок, блокировка) —
«учётная» часть строки сотрудника, поэтому вход на отставшей кассе не отменяет отключение
сотрудника или смену ПИН-кода на другой. Сотрудники базы, подключившейся к существующему
магазину (не переподключение), отключаются после загрузки данных магазина (их ПИН мог
совпасть); ПИН-код, совпавший у двух активных сотрудников, не принимается ни на одной кассе.
Сторно одного прихода, завершение одной инвентаризации и отмена одной оплаты поставщику на
двух кассах без связи учитываются один раз (строки движения/журнала с одинаковым id).
Наличную оплату поставщику отменяет только касса, в чьей смене она внесена; подсказка
суммы на начало смены берётся из своих смен. Заказы, принятые до v3, получают документ
прихода «Начальный остаток (синхронизация)». Добавлены индексы строк возврата и прихода
(проверка целостности и миграция v5 не квадратичны); обновлённый токен облака сохраняется
и после неудачной синхронизации.
Четвёртое ревью (без смены схемы): частичные возвраты считают уже возвращённое по строкам
возврата, поэтому строка возвращается до копейки; история смен — по времени открытия.
Строки проигравшей версии черновика заказа скрываются, а не удаляются, и возвращаются, если
их версия снова победит; метки скрытия одинаковы на всех кассах. Проведённая инвентаризация
и сторнированный приход «липкие» (как аннулирование), правка черновика инвентаризации не
перекрывает проведение; «липкое» значение, которое перекрыла более новая правка, отправляется
заново. Документ отправляется раньше строк его эффекта, а сервис, нашедший строку эффекта
(`effectId`) уже применённой, отказывает понятным сообщением; гарантийная замена со
списанием — тоже одноразовый эффект. Проигравшее совпадение штрихкода / карты / кода
сертификата / номера документа отправляется как правка, и номера всех нумерованных
документов (не только чеков) проверяются на совпадение после восстановления. Изменение из
облака проверяется по типам столбцов и применяется в своей точке сохранения: повреждённое
пропускается (конфликт `rejected`), версия выше 2200 года отвергается (клиент и сервер).
Резервная копия не содержит токен входа в облако.

## D-026 Облако синхронизации — Firebase (Firestore) вместо Supabase (заменяет серверную часть D-025)
Решение владельца 2026-11-26: синхронизация работает через Firebase. Движок D-025 (триггеры,
LWW, производные остатки, коды касс) не меняется — меняются только транспорт и сервер.
Вход — Firebase Authentication (e-mail/пароль, REST Identity Toolkit + Secure Token), данные —
Cloud Firestore через REST (без FlutterFire, чтобы одинаково работать на Windows и Android).
Журнал изменений: `stores/{store}/changes/{changeId}` с порядковым `seq`, выдаваемым
транзакцией по счётчику `stores/{store}.nextSeq` — поэтому порядок без «дыр» и повторная
отправка идемпотентна (id документа = changeId). Доступ — правила Firestore по членству
`stores/{store}/members/{uid}`; среда магазина (`test`/`production`) задаётся при создании и
не меняется. Тестовый проект владельца: `dreampos-test-uz26` (Firestore в регионе nam5);
рабочий проект создаётся отдельно (регион — Европа). Код и SQL Supabase удалены (история — в git).
Спецификация — `docs/specs/firebase-sync.md`, правила — `firebase/firestore.rules`, инструкция
владельцу — `docs/SYNC_SETUP.md`.
Обновление 2026-11-26: основной проект владельца — `dreampos-37b53` (аккаунт fmuzrabov, Firestore
`europe-west3`, вход по e-mail включён, правила выложены). Тестовые и боевые магазины в нём
разделены полем `environment`. `dreampos-test-uz26` (nam5) остаётся запасным тестовым проектом.
Самостоятельная регистрация по публичному ключу на тарифе Spark не отключается (нужен Identity
Platform) — чужая учётная запись не видит данных магазинов, но может создать свой магазин.
