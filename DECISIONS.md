# DreamPOS — Architecture Decision Log

Каждое решение: контекст → решение → последствия. Не меняйте принятые решения
без новой записи, которая явно отменяет старую.

## D-001 Платформа: Flutter, одна кодовая база
Касса на Windows (основной сценарий: ПК + сканер + чековый принтер), Android‑планшеты/телефоны
для мобильных продавцов и владельца. Flutter 3.38, Dart 3.10. Web пока не поддерживается
(drift на web требует wasm‑сборки sqlite — добавим при необходимости).

## D-002 Offline‑first: локальная SQLite (drift) — источник истины
Касса обязана продавать без интернета. Все операции пишутся в локальную БД
транзакционно. Облако — следующий этап (см. D-003).

## D-003 Готовность к синхронизации между кассами
Все синхронизируемые таблицы: UUID `id`, `createdAt`, `updatedAt`, мягкое удаление `deletedAt`.
Таблица `sync_outbox` фиксирует изменённые сущности (`db.markDirty`). Номера документов
(`counters`) локальные; при подключении сервера номер чека станет `<код кассы>-<номер>`.
Целевой бэкенд для синхронизации: Supabase (Postgres) — уже используется в других
проектах владельца. Не реализовано: сам транспорт синхронизации.

## D-004 Деньги — целые минорные единицы
`int` в минимальных единицах валюты. `CurrencyConfig.decimals` (UZS=0, TJS=2 …).
Никаких `double` для денег. Валюту нельзя менять после первой продажи.

## D-005 Остатки — журнал движений + кэш
`stock_movements` — неизменяемый журнал (sale/return/receipt/writeoff/adjustment/inventory).
`products.stockQty` обновляется в той же транзакции. Все изменения только через `StockService`.
Себестоимость — средневзвешенная, пересчитывается при приходе.

## D-006 Состояние и навигация
Riverpod 3 (провайдеры в `lib/core/providers.dart`), go_router (`lib/app/router.dart`),
адаптивная оболочка: NavigationRail ≥1000px, Drawer — уже.

## D-007 Доменные сервисы вне UI
`lib/domain/services/*` — вся бизнес‑логика продаж, возвратов, смен, долгов, склада.
UI никогда не пишет напрямую в таблицы sales/sale_items/stock_movements/customer_ledger.
Ошибки бизнес‑правил — `BusinessException` с текстом для пользователя.

## D-008 Политика скидок
Автоскидки по позиции не суммируются: берётся лучшая (акция на товар/категорию, N+M,
персональная скидка клиента). Ручная скидка кассира добавляется сверху и ограничена
`users.maxDiscountPercent`. Скидка на чек (акция/промокод/ручная) распределяется по
позициям пропорционально — это гарантирует точные частичные возвраты.
Цены включают НДС; НДС выделяется по позиции.

## D-009 Возвраты
Частичные возвраты по позициям; сумма возврата пропорциональна оплаченной сумме позиции,
последняя единица забирает остаток округления. Срок возврата — настройка `return_days`.
Начисленные бонусы списываются пропорционально. Аннулирование (void) — только чек без
возвратов и только в той же смене.

## D-010 Смены и касса
Продажа требует открытой смены (`require_shift`). Ожидаемая наличность =
размен + нал. продажи − нал. возвраты + внесения − выплаты/расходы/инкассации +
погашение долгов наличными − оплаты поставщикам наличными.

## D-011 Безопасность
Вход по PIN (уникален среди активных сотрудников). Хэш: итерационный SHA‑256 с солью.
Блокировка после серии неверных попыток. RBAC: `lib/core/permissions.dart`.
Журнал аудита `audit_log` для чувствительных действий (скидки, возвраты, аннулирования,
корректировки остатков, касса).

## D-012 Язык интерфейса
Сейчас русский, строки в коде. Узбекский/таджикский/английский — отдельный этап
(вынос строк в ARB через gen-l10n). Не смешивать языки на одном экране.

## D-013 Демо‑данные отделены от боевых
Демо‑данные создаются только по явному флажку в мастере установки, ставят
`demo_mode=1`, на экране входа показывается метка «Демо‑режим».

## D-014 Реальные платёжные системы и фискализация не подключаются без согласия владельца
Оплата картой/переводом фиксируется вручную (сумма + ссылка). Интеграции с эквайрингом,
OFD/фискальными модулями (Uzbekistan OFD, и т.п.) — только после решения владельца.
